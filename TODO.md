- **Cluster-count band (pool-adaptive K)**: `K_final = clamp(natural_K(τ), K_enhanced=3, K_max=15)`. Inside the band the distance guard NEVER force-merges semantically distinct clusters (the failure mode where distinct subtopics share one weight and the true optimum becomes inexpressible); beyond the cap, closest-pair forced merges (logged) keep heterogeneous pools within budget. The paper merges to a fixed K_enhanced (20 in the main experiment) regardless of distance — the band is a deliberate deviation. Diagnostics: every run PRINTS a merge-profile block after clustering (sampled distance curve, natural_K at τ∈{0.7..1.2}, elbow, and automatic tuning advice: guard-stop → OK / forced → raise cap? / floor-stop → coarser pool, stricter τ?) and writes `merge_profile.json` (same data + advice list) — the audit trail for K decisions per data pool

## Resolved Design Decisions

- **d20 ≈ CLIMB proxy**: scaling_params=435.2M, 1000 iterations, 8 parallel experiments (1 NPU each)
- **d28 target**: auto-detected from meta_*.json checkpoint, not hardcoded in DEPTH_INFO
- **Cluster-count band [3, 15] with τ=0.9**: floor 3 = permissive safety bound (coarse pools keep their natural structure instead of being pinned to 10; paper-faithful = set K_ENHANCED to the paper's fixed K_enhanced — 20 in its main experiment); cap 15 = search-budget bound for our 35-config budget (paper used 112); τ=0.9 (~cos 0.6, on L2-normalized embeddings) rejects merges of semantically distinct clusters inside the band. Paper v2 §3.1 states its own merge threshold (Euclidean 1.5, unnormalized-space — not directly comparable to ours; see docs/paper_deviations.md D5/D6); see the printed merge-profile diagnostics + merge_profile.json per pool
- **ClimbMix adaptive shards**: calc_climbmix_count(stem_docs, ratio) → ceil(stem_docs * 0.3/0.7 / 500000), clamped [3, 50] — not all 400B
- **Reverse-order download**: shards from MAX_SHARD (6542) backwards, avoids overlap with pretrain shards 0-999
- **Stream-based mixing**: stream_texts_uniform + endless_generator, memory-efficient (no full List[str] loading)
- **STEM eval metric**: --eval-benchmarks=stem → CSV "STEM" row parsed as stem_metric; SNR-weighted acc+NLL z-score (see docs/scoring_metric_design.md)
- **Proxy 并行 k 选择指南** (`docs/parallel_k_selection.md`, 2026-08-28): 生产搜索"每实验卡数 k"的决策模型与闭式规则。实测锚点: d20@1卡 60s/步 (speedrun), d28@8卡 18.2s/步 (run-4, mfu 16.71) → 加速比近线性 S(2)≈1.85/S(4)≈3.5/S(8)≈6.5; 生产单实验 T(k)=18.6/10.0/5.3/2.8h @ k=1/2/4/8 (scaling 税 +7.5%/13%/21%), eval 全量 ≈1.9h@1卡 (95% 是 gsm8k_cot+math_cot_500 生成任务)。核心结论: 吞吐 ≈A/T(1) 与 k 无关, k 只决定切片 (波长/单轮样本数/节点装箱); 迭代屏障空转 (30-80%) >> scaling 税 (7-21%) → 设计越小最优 k 越大; {nᵢ} 可自由定制时最优解 = 先定 k 再取 nᵢ 全为 C=⌊A/k⌋ 的整数倍 → Wall=T(k)·N/C 零空转。三步法: 节点装箱算 C(k) → λ_max(波长上限=不可反悔合同长度: 灾难最大损失 A·T(k) 卡时/纠偏节奏) 定 k 下限、节点形状定上限 → nᵢ 取 C 整数倍。当前决策: 首个生产 run λ_max≈5h → k=4 (speedrun 已全绿但生产仍是规模跃迁: 10B 池 embedding/1000 步全量 eval/RemoteExecutor 首战, 灾难上限 ~74 卡时@32卡池), 全绿后放宽 λ_max≈10h → k=2; k 全程固定 (分数可比性), 池波动由队列派发吸收。RemoteExecutor M4 (mixed-fleet 调度) 应实现该三步法为 launch planner
- **Continual pre-training**: all stages anneal from base checkpoint, lr_scale=1.0, warmup=0.0, warmdown=0.9
- **Random baseline = equal cluster weights (paper App. C.1)**: "each cluster is assigned an equal and uniform weight" — NOT a doc-uniform draw (that would weight clusters by natural size, i.e. feed the pool's skew). `prepare_random_baseline.py` now runs the CLIMB arm's own selector (`select_data_by_mixture`) with α_k=1/K, the same `--target-tokens` cap, and the same shortfall policy (cluster < quota → take all docs, no duplication, no redistribution — data_selector's existing behavior), so both arms degrade identically and stay comparable. The paper documents no small-cluster policy and needs none (800B tokens / 21 clusters / 40B budget → ~1.9B-token quota per cluster, only a <0.24% cluster would fall short); our smaller pools can hit shortfalls — loudly logged + recorded in `.done` (planned vs effective weights, shortfall cluster ids). Labels come from `cluster_cache.npz` with a length-mismatch hard fail (pool changed since cache); token counts from the pool's precomputed char-count column (no full-text scan of the pool)

## Known Limitations

- Resume is atomic per experiment/training run, NOT per training step: an interrupted nanochat training restarts from step 0 (partial target checkpoints are deliberately cleared before retrain)
- Fingerprint does not detect: edits inside nanochat-npu, or data files whose names/row-counts are unchanged (content swaps)
- Embedding cache staleness: pool cache keys cover (shard manifest, model, truncate len, sample-size-if-subsampled) + row-count guards on load, but a same-size content swap inside a shard still hits the old cache (same limitation as fingerprints, content-keyed by size only)
- Predictor refit on resume assumes LightGBM determinism (same accumulated data → same model); verified identical weights in local integration tests
- quality_cluster discovery breaks when K_init > number of domains (centroids shape error) — unused in production (embedding_cluster)
- NPU embedding compatibility relies on the stella buffer repair; re-verify NaN=0 after any sentence-transformers upgrade
- ClimbMix shard count is adaptive (3-50), not full 400B dataset — only enough to match 30% of STEM doc count
- d28 DEPTH_INFO requires meta_*.json checkpoint for auto-detection; without checkpoint, raises ValueError
- STEM data fact density D unknown — cannot determine if subdisciplines cross phase transition threshold
- Intentional deviations from paper documented in docs/paper_deviations.md (12 items: budget/sampling/selection/LightGBM/cluster-band/τ/random-shortfall/metric/70-30-mix/scale/chars-4/eval-cap) + docs/scoring_metric_design.md (SNR score, 70/30 anti-forgetting mix, chars/4 token estimation)
